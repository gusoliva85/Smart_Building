Backend: conexión a base de datos

Hecho

Se creó database.py con el engine de SQLAlchemy apuntando a smart_building.db, la fábrica de sesiones y la Base declarativa que van a heredar todos los modelos a partir de la Fase 1 (Usuario, Edificio, etc.). Es la última pieza de infraestructura antes de poder escribir el primer modelo real.

database.py

engine = create_engine( f"sqlite:///{RUTA_BASE_DATOS}", connect_args={"check_same_thread": False}, ) SesionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine) Base = declarative_base() def obtener_db(): """Dependencia de FastAPI: entrega una sesión por request y la cierra al final.""" db = SesionLocal() try: yield db finally: db.close()

check_same_thread=False es necesario porque SQLite por default solo permite usar una conexión desde el thread que la abrió, y FastAPI atiende cada request en su propio thread — sin este flag, la primera consulta real desde un endpoint rompería.

Tarea 9

Frontend: tokens.css y components.css

¿Qué son tokens.css y components.css?

Son dos archivos de estilos (CSS) que en conjunto definen cómo se ve toda la aplicación, separados por un motivo simple: uno guarda los "ingredientes" y el otro guarda las "piezas ya armadas" con esos ingredientes. Ninguno de los dos muestra nada por sí solo — son la base que cada pantalla real (login, dashboard, reclamos...) va a usar para no tener que inventar su propio estilo de botón o de tarjeta cada vez.

tokens.css — el diccionario de materiales Es una lista de "variables": acá decimos, una sola vez, qué color exacto es el "verde de estado", qué color es el "acento de marca", cómo es la sombra de una tarjeta, cómo es el efecto vidrio. No dibuja ningún botón ni tarjeta — solo declara los valores. Incluye la versión de cada valor para tema claro y para tema oscuro.
components.css — el catálogo de piezas Usa esos mismos ingredientes para armar las piezas visuales completas y reutilizables: la tarjeta de vidrio, la barra superior, la tarjeta de KPI, el semáforo de colores, el panel de detalle. Cada pantalla nueva elige piezas de este catálogo en vez de diseñar una tarjeta "a su manera".

La ventaja concreta: si mañana se decide ajustar el tono del color de "atención" (amarillo), se cambia un solo valor en tokens.css y automáticamente se actualiza en cada tarjeta, chip y borde de toda la aplicación que use ese estado — nadie tiene que salir a buscar dónde quedó ese color "pegado" a mano en 15 archivos distintos.

tokens.css — extracto

:root{ /* Semáforo funcional — idéntico en ambos temas, nunca decorativo */ --ok:#2e8067; /* verde */ --warn:#ba8c1f; /* amarillo */ --pend:#bd6c2c; /* naranja */ --crit:#b13c47; /* rojo */ /* Acento de marca — acero/grafito, nunca se parece al semáforo */ --accent:#57768c; --accent-2:#3e5a6d; } html[data-theme="dark"]{ --accent:#7ea3ba; --accent-2:#9bc0d4; /* el semáforo NO cambia con el tema: el significado de un estado no puede depender de si el usuario eligió modo oscuro o claro */ }

Tarea 11

Frontend: assets/js/api.js

Hecho

Wrapper único de fetch() para hablar con el backend. Centraliza acá lo que, si no, se repetiría en cada pantalla futura: la URL base de la API, agregar el token de sesión guardado en localStorage, convertir la respuesta a JSON y manejar los errores siempre de la misma forma — incluido el caso "el backend no está corriendo", que hoy es el más probable ya que todavía no hay login.

api.js — núcleo

const API_BASE_URL = 'http://127.0.0.1:8000/api'; async function apiFetch(ruta, opciones = {}) { const token = obtenerToken(); const encabezados = { 'Content-Type': 'application/json', ...(opciones.headers || {}) }; if (token) encabezados['Authorization'] = `Bearer ${token}`; let respuesta; try { respuesta = await fetch(`${API_BASE_URL}${ruta}`, { ...opciones, headers: encabezados }); } catch (error) { // ni siquiera hubo respuesta: el backend no está corriendo, o CORS lo bloqueó throw new Error('No se pudo conectar con el servidor. Verificá que el backend esté corriendo.'); } if (respuesta.status === 401) { borrarToken(); location.href = 'index.html'; // listo para la Fase 1, hoy no se dispara todavía throw new Error('Sesión inválida o expirada.'); } // ...castea a JSON y lanza con el mensaje del backend si respuesta.ok es falso } window.Api = { get, post, put, patch, eliminar, guardarToken, borrarToken, obtenerToken };

_contexto_password = CryptContext(schemes=["bcrypt"], deprecated="auto") def hashear_password(password: str) -> str: return _contexto_password.hash(password) def verificar_password(password: str, password_hash: str) -> bool: return _contexto_password.verify(password, password_hash) def crear_token_acceso(datos: dict, minutos_expiracion=JWT_MINUTOS_EXPIRACION) -> str: a_codificar = dict(datos) a_codificar["exp"] = datetime.now(timezone.utc) + timedelta(minutes=minutos_expiracion) return jwt.encode(a_codificar, JWT_SECRETO, algorithm=JWT_ALGORITMO) def decodificar_token(token: str) -> dict: try: return jwt.decode(token, JWT_SECRETO, algorithms=[JWT_ALGORITMO]) except JWTError as error: raise TokenInvalido(str(error)) from error
Problema real encontrado al correr los tests, y cómo se resolvió

Al correr los tests, hashear_password() falló para los tres casos que usan contraseñas de verdad (no para los de JWT, que no dependen de bcrypt). La causa: passlib (la librería que pide el Documento Técnico) no tuvo una actualización en varios años, y la versión más nueva de bcrypt que se instaló por default le eliminó un atributo interno (bcrypt.__about__) que passlib necesita para autodetectarse — es un problema de compatibilidad conocido entre esas dos librerías, no un error del código del proyecto.

Solución: se fijó una versión de bcrypt anterior a la 4.1 (quedó en 4.0.1), que sí es compatible con la versión de passlib usada. No se cambió de librería — se mantiene Passlib tal como lo pide el Documento Técnico (sección 2.2), solo se fijó la versión de su dependencia.

Frontend: barrido circular del toggle de tema

Hecho

El botón de "Cambiar tema" (topbar, todas las pantallas) ahora anima un barrido circular que nace del punto exacto del clic y crece hasta cubrir toda la pantalla, en vez del cross-fade genérico del navegador. Es exactamente el refinamiento que la skill premium-uiux (componentes.md, sección "Toggle de tema") y el Roadmap (Fase 12) ya dejaban documentado como pendiente — se adelantó a pedido explícito, fuera de su orden normal en el Roadmap.

De dónde salió la idea y cómo se adaptó

El pedido llegó con el código de referencia de AnimatedThemeToggler, un componente de la librería Magic UI pensado para proyectos React/Next.js (usa useState, flushSync de React y un import @/registry/... que no existe fuera de ese ecosistema). Este proyecto es HTML/CSS/JS vanilla sin build ni framework (Documento Técnico, sección 1.3.1), así que se tomó la técnica del componente — no el código React — y se reescribió en JavaScript plano dentro de assets/js/theme.js, el mismo archivo que ya manejaba el toggle antes.

La técnica: View Transitions API + Web Animations API

La View Transitions API (document.startViewTransition) congela una "foto" del estado anterior de la página. Encima de eso, se anima con Element.animate() un clip-path: circle() que crece desde 0px hasta un radio que cubre toda la pantalla (calculado con el teorema de Pitágoras hasta la esquina más lejana del punto de clic), aplicado sobre el pseudo-elemento ::view-transition-new(root) — el "estado nuevo" de la página. El resultado visual: el tema nuevo se revela como un círculo que se expande desde el botón, tapando el tema anterior.

const { clientX: x, clientY: y } = evento; const radioMaximo = Math.hypot( Math.max(x, window.innerWidth - x), Math.max(y, window.innerHeight - y), ); const transicion = document.startViewTransition(aplicar); transicion.ready.then(() => { raiz.animate( { clipPath: [`circle(0px at ${x}px ${y}px)`, `circle(${radioMaximo}px at ${x}px ${y}px)`] }, { duration: 550, easing: 'ease-in-out', pseudoElement: '::view-transition-new(root)' }, ); });

En CSS (components.css) se anula el cross-fade por defecto que el navegador aplica solo, y se asegura que el círculo que crece (el estado nuevo) quede siempre por encima del estado anterior:

::view-transition-old(root), ::view-transition-new(root){ animation:none; mix-blend-mode:normal; } ::view-transition-old(root){ z-index:1; } ::view-transition-new(root){ z-index:2; }

De paso: el ícono ahora refleja el tema real

Antes el botón mostraba siempre el mismo ícono de sol, sin importar el tema activo. Se agregó un ícono de luna (mismo estilo SVG a mano que el resto de la skill: viewBox 24x24, trazo, sin relleno) y theme.js ahora intercambia el contenido del <svg> según data-theme — sol en tema claro, luna en tema oscuro — tanto al cargar la página como en cada clic.

Bug encontrado al probar: el barrido solo se veía yendo de oscuro a claro

La primera versión del CSS invertía el z-index de los dos "estados congelados" cuando el tema nuevo era oscuro (html[data-theme="dark"]::view-transition-old(root){ z-index:2 }, pensado copiando un patrón de otra variante de esta técnica que no aplica acá). El efecto: al pasar de claro a oscuro, el círculo que crece (el estado nuevo) quedaba debajo del estado anterior — invisible durante toda la animación — y recién se veía el cambio al final, de golpe, sin barrido. De oscuro a claro sí se veía bien, porque en ese caso la regla no se activaba. Se sacaron esas dos líneas condicionales: el estado nuevo va siempre arriba, sin importar la dirección. Verificado con capturas a los 60ms y 150ms del clic en ambas direcciones — ahora se ve el círculo creciendo desde el botón en los dos sentidos, por igual.

Verificación con Playwright, contra la app real

  • Estado inicial: tema claro, ícono de sol. Tras el clic: data-theme="dark" aplicado, ícono cambiado a luna, sin errores de consola ni de página.
  • Capturas a 60ms y 150ms del clic muestran el círculo oscuro creciendo desde el botón (claro→oscuro) y el círculo claro creciendo desde el botón (oscuro→claro) — ambas direcciones simétricas tras la corrección.
  • Captura final confirma el tema oscuro aplicado correctamente en topbar, tarjeta de login y botones — mismos tokens de color de siempre, ningún valor pegado al tema anterior.
